# API contracts

All paths below have `/api` prefix. JSON request bodies are limited to 32 KB. Object identifiers must be 24 hexadecimal characters. JSON success responses contain a document, list, summary, or `{ok:true}`. Errors are `{error, requestId}` where available; rate-limit errors also use JSON. Validation is HTTP 400, unauthenticated 401, forbidden 403, missing record 404, conflicts 409, abuse 429, unexpected failures 500. Oversized bodies return 413. Financial summaries outside the supported safe-integer range are refused with 503.

## Authentication and mutation headers

Login requires the configured `Origin`. Protected endpoints require the HTTP-only session cookie. All protected mutations require configured `Origin` and `X-CSRF-Token` obtained from login or `/auth/me`. Retry-sensitive business mutations additionally require `Idempotency-Key` (8–100 word/hyphen characters; random UUID recommended). Never put credentials in a URL.

| GET /reports/inventory | Manager/Admin | `page`; current active product stock, not date-filtered |

Lists return `{items,total,page,limit}`. Default catalog/customer page size is 20, maximum 100; page numbers are 1–10,000. Sort values other than `name` use newest-first. Reports return `{summary,items,truncated}`; detail rows and exports cap at 1,000 while summary includes all matches. Date boundaries use Asia/Kolkata and include the end day. Payment detail pages are fixed at 20 rows.

Example create-order body (synthetic IDs only):

```json
{"customer":"aaaaaaaaaaaaaaaaaaaaaaaa","items":[{"product":"bbbbbbbbbbbbbbbbbbbbbbbb","quantity":2}]}
```

An idempotent replay returns the originally committed response and original endpoint success code. It is not a fresh read of the entity's current state. Read the entity endpoint to obtain subsequent changes.

Idempotency keys apply to customer/catalog create and update, stock adjustment, order creation and transitions, payment additions/reversals, and user create/update. Authentication endpoints use their session/CSRF controls and do not require these keys. Search on customer/catalog lists matches names; order search matches number or the saved customer name. CSV export is generated by the browser from bounded report rows, not a separate API endpoint.

Customer edits atomically match the supplied `version` and increment it on success. A stale edit returns HTTP 409 with `{error,code:"EDIT_CONFLICT",requestId}`; missing/invalid versions return 400. Reload the latest customer, review the retained local edits, and submit with its latest version and a fresh idempotency key. No new database index or migration is required: the existing `_id` index identifies the document before checking its version. Order confirmation also advances the customer version, so confirmation can legitimately cause an edit conflict.

Dashboard defaults to the existing rolling 30-day daily trend. Monthly mode returns six calendar-month buckets, including zero months, using Asia/Kolkata midnight boundaries. `month` selects the ending calendar month, defaulting to the current business month. The additive `trendPeriod` object supplies `mode`, `start`, `endExclusive` (null for the original daily view), `timezone` and the selected-period `total`. KPI `totals` remain all-time; trend dates are order creation dates for currently confirmed/fulfilled orders. Reporting selection does not provide historical mutation/backdating capabilities.

## Verification boundary

This inventory was reviewed against local route definitions. The release suite passed 18 backend tests and 15 Chrome cases; coverage is listed in [verification.md](verification.md). Those tests exercise representative contracts and failure cases, not every endpoint/input permutation. External database operation and deployed HTTPS/proxy behavior remain unverified.
